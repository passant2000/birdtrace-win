## 一、项目背景与当前基线

BirdTrace 当前开发基线为 v0.8.6，是一个以 Windows 便携版为主要交付目标的鸟类摄影作品管理软件，技术栈为 PySide6 + SQLite。

项目定位：

- BirdTrace 主要管理 Photoshop、Lightroom 等后期处理完成后的鸟类摄影成品照片。
- 它不是 RAW 管理器，也不是 Lightroom、Photoshop 插件，不负责图像后期处理。
- 但不能完全排除 RAW/DNG：已经确定支持 DxO DNG + JPG 成对编目。RAW/DNG 可以作为成品照片的附属文件参与关联和编目，也可以作为识别输入，但不围绕 RAW 建立完整的后期处理、筛选、预览和管理工作流。
- 原始成品图片是用户作品，BirdTrace 不得擅自修改原图。水印、分享卡等功能应生成新文件。
- 核心价值是成品照片管理、AI 鸟种识别、人工纠错、多鸟种归档、个人鸟类摄影档案、统计、地图、时间线和年度回顾/分享。

### 当前已有能力和不可重复建设的部分

1. 已支持 JPG、PNG、TIFF、WebP 等格式，实际支持范围还包括 HEIC、HEIF、MPO、BMP 等，具体以源码为准。
2. 引用、复制、移动三种导入模式已经实现。
3. `.birdtrace.json` Sidecar 已落地，具备 hash 键、已有编辑优先、评分同步等能力。
4. 一张照片对应多个鸟种已经实现。现有 `records` 表承担 photo × species 多对多关系，包含 rank、confidence、source、box_json、confirmed_code 等字段。
5. 人工确认优先于 AI 识别，重新识别不得覆盖人工确认结果。已有组级改判机制，不要另造一套重复机制。
6. relink、hash 自动恢复、missing 状态、离线横幅等路径与离线韧性功能已经存在。
7. 鸟种图鉴、地图、时间线已有较丰富能力，包括最美照片、罕见度、迁徙、鸟种胶囊等。
8. 水印、分享卡、批量导出已经在 0.8.3–0.8.6 经过多轮打磨，已有导出向导三种模式。
9. pHash 已全库落库，0.9.0 开发清单已经包含重复检测。
10. 已有 `verify_*`、`assert_pkg`、`frozen_check` 和冒烟测试等测试体系。
11. `docs/PROGRESS.md` 和 `docs/后续开发方案.md` 是项目当前进度与开发计划的权威活文档。必须先阅读，不能把已完成工作重新包装成新任务。

### 必须遵守的开发红线

- 不新建 `PhotoSpecies`、`Sighting`、`ObservationSession` 等重复模型。现有 `records` 表已经实现照片与鸟种的多对多关系。
- 不做 repositories/services/models 分层重构。当前 `ai/core/ui/db.py` 结构已经够用，不为架构美观进行大规模重写。
- 不改变已经确认的 0.9.0 开发清单顺序。
- 不重写已经成熟的识别管线；识别相关新功能只能通过现有接口接入。
- 人工确认结果必须优先于 AI 结果。
- Sidecar 必须保持兼容，遵守已有编辑优先原则。
- 原图绝不允许被静默修改、覆盖或删除。
- 数据库变更采用渐进迁移：先备份、只加不删、迁移前后计数校验，并提供失败回滚路径。
- 保持本地优先、轻量、适合 Windows 便携版，不引入没有必要的后台服务。
- 所有新功能都必须提供功能级自动化验证脚本或等效测试。

# 专题 1：导入事务、失败回滚、导入任务日志与格式魔数校验

## 1. 目标

增强现有导入流程的可靠性，避免出现以下情况：

- 文件已经复制或移动到图库目录，但数据库登记失败；
- 数据库已经登记，但 Sidecar 应用失败；
- 程序在导入中途崩溃，留下无法判断状态的文件；
- 用户取消导入后，文件和数据库状态不一致；
- 扩展名正确但文件内容损坏或格式不匹配；
- 清理失败文件时误删用户已有文件。

已知当前源码中的 `import_files()` 流程需要重点核实：当前实现先执行 `shutil.copy2()` 或 `shutil.move()`，再调用图库数据库登记；单文件异常时主要计入 failed，缺少完整的事务补偿；导入结束后才应用 Sidecar。请在真实工作树再次确认，不要直接假定旧源码与当前版本完全一致。

## 2. 明确不做的事

- 不把整个批次设计成一个跨文件系统的大事务。
- 不改变现有三种导入模式：引用、复制、移动。
- 不重写现有数据库模型和识别管线。
- 不因为 Sidecar 写入失败就删除已经成功入库的照片。
- 不允许移动模式在目标端尚未可靠入库前就不可逆地删除源文件。
- 不允许清理不属于本次任务创建的文件。

## 3. 数据结构建议

建议增加任务级和文件级日志表。

### import_jobs

建议字段：

- `job_id TEXT PRIMARY KEY`
- `batch_id TEXT`
- `mode TEXT`
- `source_root TEXT`
- `dest_root TEXT`
- `status TEXT`
- `cancel_requested INTEGER DEFAULT 0`
- `started_at TEXT`
- `finished_at TEXT`
- `total_count INTEGER DEFAULT 0`
- `success_count INTEGER DEFAULT 0`
- `skipped_count INTEGER DEFAULT 0`
- `failed_count INTEGER DEFAULT 0`
- `error_summary TEXT`

### import_job_files

建议字段：

- `id INTEGER PRIMARY KEY`
- `job_id TEXT`
- `source_path TEXT`
- `target_path TEXT`
- `file_hash TEXT`
- `file_size INTEGER`
- `source_mtime REAL`
- `status TEXT`
- `operation TEXT`
- `error_code TEXT`
- `error_message TEXT`
- `started_at TEXT`
- `finished_at TEXT`
- `UNIQUE(job_id, source_path)`

外键、索引和字段类型应结合当前 SQLite 迁移规范确定。

### 文件状态建议

可以使用以下状态，具体命名允许根据现有代码调整，但状态含义必须明确：

`pending → validated → staged → file_ready → db_committed → sidecar_applied → done`

异常或中断状态包括：

`skipped`、`failed`、`rollback_pending`、`rolled_back`

任务级状态至少应能区分运行中、完成、部分完成、失败、已取消和待恢复。

## 4. 导入流程建议

### 引用模式

- 不复制、不移动源文件。
- 验证文件后登记数据库。
- 数据库登记失败只记录失败，不得触碰源文件。

### 复制模式

建议采用：

1. 验证源文件。
2. 复制到目标目录下的临时文件。
3. 校验目标文件大小，必要时校验 SHA-256。
4. 将临时文件原子重命名为最终目标文件。
5. 登记数据库。
6. 数据库登记成功后，才将文件任务标记为已提交。
7. 数据库登记失败时，只清理本次任务创建的目标文件，并再次确认其路径和 hash 与任务日志一致，防止误删用户已有文件。

### 移动模式

不能简单地先 `shutil.move()`，然后再登记数据库。

建议采用更安全的补偿式流程：

1. 先复制源文件到目标临时文件。
2. 校验目标文件。
3. 原子重命名为目标文件。
4. 登记数据库。
5. 数据库登记成功后，才尝试清理源文件。
6. 源文件清理失败时，目标文件仍保持入库成功，同时记录源文件清理警告，不得破坏目标端已提交数据。

这样可以避免数据库登记失败时源文件已经丢失。

### Sidecar 顺序

- 先完成照片文件和数据库登记。
- 再应用 Sidecar。
- Sidecar 失败时保留照片入库结果，记录待重试状态。
- 不应因为 Sidecar 失败回滚已经成功的照片导入。

## 5. 取消与崩溃恢复

### 取消语义

- 用户取消后，不再启动新的文件任务。
- 当前文件应执行到一个安全检查点。
- 已经提交成功的文件保留。
- 未完成文件根据 journal 状态进行安全清理或等待恢复。
- 整个任务应能标记为部分完成，而不是假装所有文件都成功或全部回滚。

### 崩溃恢复

程序启动时检查非终态导入任务：

- 根据任务日志判断文件是否已经复制、重命名、登记数据库或应用 Sidecar。
- 检查目标文件是否存在。
- 必要时核对文件 hash。
- 检查数据库是否已经存在对应照片记录。
- 根据实际状态决定继续、补登记、补应用 Sidecar 或安全清理。
- 无法确定文件归属时宁可保留并报告，也不能冒险删除。

## 6. 格式魔数校验

不能只依赖文件扩展名。

- 对支持格式做轻量文件头检查。
- 发现扩展名与实际格式不匹配时，给出明确提示。
- 文件损坏或无法识别时，将该文件单独标记为失败或跳过。
- 单个文件校验失败不得中断整个批次。
- 不应为了校验而修改原始文件。

## 7. 边界用例与自动化断言

至少覆盖：

1. 引用模式数据库登记失败，源文件仍存在且内容不变。
2. 复制模式目标文件创建成功但数据库登记失败，任务创建的副本被安全清理。
3. 复制模式目标文件已存在且不属于本任务，失败清理不得删除它。
4. 移动模式数据库登记失败，源文件仍然存在。
5. 移动模式数据库登记成功但源文件删除失败，目标记录仍有效，任务有警告。
6. 目标文件复制过程中崩溃。
7. 目标文件原子重命名后、数据库登记前崩溃。
8. 数据库登记后、Sidecar 应用前崩溃。
9. Sidecar 应用失败，照片仍然保持入库成功。
10. 用户取消后不再启动新的文件任务。
11. 任务恢复时能识别已提交文件，不重复导入。
12. 目标文件 hash 与 journal 记录不一致时，不得自动删除。
13. 扩展名与魔数不匹配。
14. 文件内容损坏。
15. 单个文件权限错误不影响批次其他文件。
16. 并发重复导入时不产生重复记录或错误删除。

## 8. 验收标准

- 每个文件的物理文件状态、数据库状态和任务日志状态可以相互核对。
- 中断后可恢复或明确报告，不能留下不可解释的静默状态。
- 移动模式不会在数据库提交前删除源文件。
- 回滚只处理本任务创建且能验证归属的文件。
- Sidecar 失败不会破坏已入库照片。
- 每项关键状态转换都有自动化验证。

# 专题 2：开源许可与第三方声明合规矩阵

为 BirdTrace 正式发布建立清晰的许可证与第三方组件声明体系，避免主程序代码、第三方依赖、模型权重、数据集和在线服务的许可关系混淆。

# 专题 3：常用目录增量扫描

## 1. 目标

增加一个轻量的常用目录增量扫描功能，帮助用户手动检查常用照片目录中的新增、修改、消失和移动文件。

这是一个低优先级、轻量型功能，不做后台实时文件监控。

核心原则：

- 用户手动触发扫描。
- 先用路径、文件大小、mtime 做快速判断。
- 只有必要时才计算 SHA-256。
- 复用现有 `photos.path`、`photos.file_hash`、missing 和 relink 机制。
- 不重复导入已有文件。
- 绝不修改、移动或删除用户源文件。

## 2. 明确不做的事

- 不做实时后台文件夹监控。
- 不常驻后台轮询。
- 不引入重量级文件索引服务。
- 不为扫描建立一套与现有照片表重复的完整文件数据库。
- 不自动覆盖数据库中已有照片。
- 不因为一次扫描失败就把大量照片标记为 missing。
- 不自动移动、重命名或删除用户文件。

## 3. 数据结构建议

建议只增加轻量扫描配置和扫描记录。

### scan_roots

用于保存用户设置的常用目录。

建议字段：

- `id INTEGER PRIMARY KEY`
- `root_path TEXT NOT NULL`
- `display_name TEXT`
- `enabled INTEGER DEFAULT 1`
- `last_scan_at TEXT`
- `created_at TEXT`
- `updated_at TEXT`

### scan_runs

用于记录每次扫描结果。

建议字段：

- `id INTEGER PRIMARY KEY`
- `root_id INTEGER`
- `started_at TEXT`
- `finished_at TEXT`
- `status TEXT`
- `total_count INTEGER DEFAULT 0`
- `new_count INTEGER DEFAULT 0`
- `changed_count INTEGER DEFAULT 0`
- `missing_count INTEGER DEFAULT 0`
- `relink_candidate_count INTEGER DEFAULT 0`
- `error_count INTEGER DEFAULT 0`
- `error_summary TEXT`

不要为了记录扫描而复制一套完整的照片文件状态表。现有 `photos` 表仍是照片身份与路径状态的核心。

## 4. 扫描识别流程

建议按以下层次判断：

1. 路径；
2. 文件大小；
3. mtime；
4. 必要时 SHA-256。

如果文件路径、大小和 mtime 都没有变化，可以跳过完整 hash 计算。

如果路径或文件属性发生变化，再按实际情况计算 hash。

如果 `file_hash` 已存在，应充分复用已有记录，避免无意义的重复哈希。

## 5. 四种情况的处理规则

### 情况一：新增文件

条件：

- 扫描范围内发现文件；
- 数据库中不存在对应路径；
- 根据必要的 hash 检查，也没有发现已存在的相同文件。

处理：

- 将其列为新增候选；
- 用户确认后复用现有 importer 导入；
- 不另造一套导入流程。

### 情况二：同路径文件内容发生变化

条件：

- 数据库中已有该路径；
- 文件大小或 mtime 发生变化；
- 重新计算 SHA-256 后发现内容与原记录不同。

处理：

- 标记为内容变化候选；
- 明确提示用户；
- 不得静默覆盖原照片记录或替换文件。
- 如果 hash 相同，说明可能只是时间戳或文件元数据发生变化，应避免误判成新照片。

### 情况三：文件消失

只有同时满足以下条件，才能考虑将数据库记录标记为 missing：

- 扫描根目录本身可访问；
- 目录枚举完整成功；
- 扫描没有被取消；
- 没有权限错误或严重 I/O 错误；
- 文件确实不在本次完整扫描覆盖范围内。

必须区分：

- 文件确实被用户移走或删除；
- 外置硬盘离线；
- 盘符变化；
- 目录权限不足；
- 杀毒软件锁定文件；
- 扫描过程中发生 I/O 错误；
- 用户取消扫描。

如果扫描根目录离线、枚举不完整或发生错误，不得将整批照片错误地标记为 missing。

### 情况四：文件移动或改名

如果新路径文件的 hash 命中数据库中的 missing 照片：

- 将其列为 relink 候选；
- 用户确认后调用现有 relink 机制；
- 不要重新建立重复照片记录。

如果旧路径仍然存在，而新路径只是同 hash 的另一份副本：

- 应识别为重复副本候选；
- 不要擅自把原记录的 path 改成新路径；
- 交由用户决定如何处理。

## 6. 特殊边界

必须考虑：

- 外置硬盘盘符发生变化；
- 目录离线；
- 扫描过程中用户拔掉硬盘；
- 文件被杀毒软件锁定；
- 单个文件没有读取权限；
- 文件扫描过程中被其他程序修改；
- 用户取消扫描；
- 同一 hash 出现在多个目录；
- 扫描目录中存在临时文件；
- 符号链接或目录嵌套导致重复遍历；
- 文件名包含中文或特殊字符。

不能因为一个文件读取失败，就把它当成已消失文件。

## 7. 边界用例与自动化断言

至少覆盖：

1. 新文件被识别为新增候选。
2. 新文件 hash 已存在时不重复导入。
3. 同路径、同大小、同 mtime 时跳过不必要的 hash。
4. 同路径内容变化时识别为修改候选。
5. 文件元数据变化但 hash 不变时不误判为新照片。
6. 完整扫描确认文件消失后，才允许标记 missing。
7. 扫描根目录离线时不批量标记 missing。
8. 扫描被取消时不把未扫描区域标记为 missing。
9. 单个文件权限错误不导致其他文件误判 missing。
10. 外置硬盘盘符变化时能产生 relink 候选。
11. 移动或改名后的文件 hash 命中 missing 记录时复用现有 relink。
12. 旧路径仍然存在时，新路径相同 hash 不自动替换旧路径。
13. 扫描过程中源文件发生变化时，不产生错误结论。
14. 重复扫描同一目录不会重复生成照片记录。

## 8. 验收标准

- 扫描必须由用户手动触发。
- 常见无变化文件不需要重复计算 SHA-256。
- 新增、修改、消失和移动四种情况能正确区分。
- 离线、权限错误和扫描取消不会造成错误 missing。
- 新增文件复用现有 importer。
- 移动文件复用现有 relink。
- 不修改用户源文件。

# 专题 4：重复照片检测第三层评估

## 1. 目标

评估现有 SHA-256 + pHash 重复照片检测是否需要第三层相似度判断。

现有能力：

- SHA-256 用于识别完全相同的文件内容；
- pHash 已全库落库；
- 0.9.0 开发清单已经包含重复检测；
- pHash 可用于感知相似度候选筛选。

这次重点不是为了增加算法而增加算法，而是评估第三层是否真正有必要。

## 2. 明确不做的事

**当前建议：1.0 不增加第三层相似度算法。**

不为了技术复杂度引入：

- 多裁切 pHash 聚合；
- pdHash；
- 局部特征匹配；
- 图像 embedding；
- 复杂的视觉相似度模型；
- 自动删除或自动合并机制。

除非真实测试证明现有 SHA-256 + pHash 明显不足，否则不应把第三层加入 1.0。

## 3. 评估内容

如果要研究第三层，需要比较：

| 方案           | 评估重点                      |
| ------------ | ------------------------- |
| 多裁切 pHash 聚合 | 能否识别裁切后的同一张照片，计算成本如何      |
| pdHash       | 与现有 pHash 相比是否有明显收益       |
| 局部特征         | 是否能识别不同尺寸、局部裁切和编辑后的相似照片   |
| embedding    | 是否会把同一只鸟的不同构图、同一场景连拍误判成重复 |

需要特别注意：

- 同一只鸟的不同照片不是重复照片；
- 同一场景的不同构图不是重复照片；
- 连拍中的不同瞬间不应被误合并；
- 不同裁切、调色、缩放后的同一张照片可能需要识别；
- 一万张以上图库的计算成本和响应时间必须考虑。

## 4. 安全原则

无论未来是否增加第三层：

- 算法只能提供疑似重复候选；
- 不得自动删除文件；
- 不得自动合并数据库记录；
- 不得自动跳过用户导入的照片；
- 必须由用户人工确认；
- 不能破坏原图和已有人工编辑结果。

## 5. 边界用例与自动化断言

如果未来决定实施，至少测试：

1. 同一张照片仅改变文件名。
2. 同一张照片改变 JPEG 压缩质量。
3. 同一张照片缩放尺寸。
4. 同一张照片轻微裁切。
5. 同一张照片大幅裁切。
6. 同一只鸟在不同时间拍摄的照片。
7. 同一场景中不同构图的照片。
8. 连拍中鸟的姿态发生变化。
9. 不同照片具有相近背景。
10. 一万张照片规模下的计算时间和内存占用。

## 6. 验收标准

本专题允许得出“不做”的结论。

如果现有 SHA-256 + pHash 已足够，则只需记录评估结果和暂缓原因，不增加代码、不增加数据库结构、不影响 1.0 进度。

# 专题 5：版权信息字段集与三处映射

## 1. 目标

建立统一的版权信息来源，使版权信息能够在以下位置保持一致：

1. BirdTrace 图库中的照片信息展示；
2. 照片 XMP/IPTC 元数据；
3. 分享卡、导出图片等输出内容。

支持：

- 图库级默认版权信息；
- 照片级单独覆盖；
- Sidecar 保存；
- 分享卡署名；
- 可选的 XMP/IPTC 写回。

核心要求是避免同一版权信息在不同功能中出现多套互相矛盾的来源。

## 2. 明确不做的事

- 默认不修改原始照片元数据。
- 不在用户没有明确同意时写回 XMP/IPTC。
- 不把分享卡中的摄影者字段继续作为一套独立、互不关联的版权来源。
- 不因某张照片没有单独设置版权信息，就丢失图库级默认值。
- 不允许简单使用 SQL `COALESCE` 处理所有字段，因为需要区分“继承”“覆盖”和“明确清空”。

## 3. 字段集建议

建议支持以下字段：

| 字段                 | 含义        |
| ------------------ | --------- |
| creator            | 创作者 / 摄影者 |
| creator_job_title  | 创作者职务     |
| copyright_owner    | 版权持有人     |
| copyright_notice   | 版权声明      |
| credit_line        | 署名 / 来源标注 |
| rights_usage_terms | 使用条款      |
| rights_url         | 权利信息链接    |
| source             | 来源        |
| contact_email      | 联系邮箱      |
| contact_url        | 联系网址      |

字段命名可根据现有项目风格调整，但要保持统一语义。

## 4. 数据结构建议

建议采用两层数据：

### copyright_defaults

保存图库级默认版权信息。

建议字段：

- `id INTEGER PRIMARY KEY`
- `creator TEXT`
- `creator_job_title TEXT`
- `copyright_owner TEXT`
- `copyright_notice TEXT`
- `credit_line TEXT`
- `rights_usage_terms TEXT`
- `rights_url TEXT`
- `source TEXT`
- `contact_email TEXT`
- `contact_url TEXT`
- `updated_at TEXT`

### photo_copyright

保存照片级覆盖信息。

建议字段：

- `photo_id INTEGER PRIMARY KEY`
- 各版权字段对应的值；
- 各字段对应的覆盖状态；
- `updated_at TEXT`

照片级字段必须能表达三种状态：

1. 继承图库默认值；
2. 使用照片级覆盖值；
3. 明确清空，不继承图库默认值。

不能只靠字段是否为 NULL 来推断所有状态。

## 5. 统一读取接口

建议提供统一的：

`effective_copyright(photo_id)`

由该接口计算最终有效版权信息。

读取优先级建议：

1. 照片级明确覆盖；
2. 照片级明确清空；
3. 照片级继承图库默认值；
4. 必要时可选读取 EXIF Artist 作为兼容性 fallback，但必须明确优先级，不能让 EXIF 值意外覆盖用户设置。

静态图库展示、XMP/IPTC 写回、分享卡生成都必须调用统一结果，不能各自实现一套字段合并逻辑。

## 6. Sidecar 兼容

- 版权信息需要支持写入 `.birdtrace.json`。
- 保留现有 Sidecar 格式兼容。
- 不得覆盖 Sidecar 中已有的用户编辑。
- 需要定义旧版本 Sidecar 读取和新版本写入规则。
- Sidecar 导入、导出必须能正确保留继承、覆盖和明确清空三种状态。

## 7. XMP/IPTC 写回

默认关闭，必须由用户明确开启。

实现前先核实实际使用的元数据工具、现有 EXIF 读取写入方式以及支持的字段映射。

必须考虑：

- 中文 UTF-8 编码；
- IPTC-IIM 字段长度限制；
- XMP 字段映射；
- 写回失败时原图不损坏；
- 只读文件；
- 写回前备份或采用安全临时文件策略；
- 写入后验证内容；
- 不支持的字段不能静默截断或丢弃；
- 用户没有开启写回时，任何功能不得修改原图元数据。

如果无法安全写回，应明确报告失败，而不是冒险覆盖原图。

## 8. 分享卡映射

现有分享卡中的摄影者/拍摄者设置应迁移到统一版权来源。

建议优先级：

1. 照片级 creator；
2. 图库级 creator；
3. 可选的 EXIF Artist fallback。

分享卡应从 `effective_copyright(photo_id)` 取得信息，避免出现图库显示一个名字、分享卡又显示另一个名字的情况。

## 9. 边界用例与自动化断言

至少覆盖：

1. 照片未设置版权信息时继承图库默认值。
2. 照片级 creator 覆盖图库级 creator。
3. 照片级明确清空 creator 后，不再继承图库默认值。
4. 照片级只覆盖一个字段，其余字段继续继承。
5. 修改图库默认值后，继承型照片显示新值。
6. 已覆盖字段不受图库默认值变化影响。
7. Sidecar 导出后再导入，版权状态保持一致。
8. 旧版 Sidecar 不包含版权字段时能正常读取。
9. 中文版权信息写入和读取保持一致。
10. IPTC 字段长度超限时明确提示，不静默截断。
11. XMP/IPTC 写回失败时原图保持完整。
12. 只读文件写回失败时不破坏照片。
13. 用户未开启写回时原图 hash 不发生变化。
14. 静态图库展示与分享卡使用相同的有效版权信息。
15. 照片级明确清空状态能正确跨 Sidecar 保存。

## 10. 验收标准

- 版权信息只有一套统一的有效值计算逻辑。
- 图库默认值和照片级覆盖关系明确。
- 继承、覆盖、明确清空三种状态均可持久化。
- Sidecar 能正确保存和恢复。
- 分享卡与图库显示一致。
- XMP/IPTC 写回默认关闭。
- 原图安全得到保证。
- 版权字段映射有文档说明。

# 专题 6：观鸟记录中心导出“数量”字段

## 1. 目标

目前 `records` 表表达的是照片与鸟种之间的识别关系，不代表某次观测中实际看到的个体数量。

但观鸟记录中心导出的 Excel 模板可能要求每个鸟种提供数量。

需要解决导出数量填写问题，同时避免破坏现有识别数据模型。

## 2. 明确不做的事

**1.0 推荐采用导出时临时编辑数量，不将数量写入数据库。**

不建议直接给现有 `records` 表增加 `count` 字段。

原因：

- `records` 是照片 × 鸟种的识别关系；
- 一张照片中出现一个鸟种，不等于现场只观察到一只；
- 一张照片可能只拍到鸟群中的一部分；
- 识别记录不等同于观测事件；
- 如果未来需要持久化观测数量，应先设计真正的 observation event 概念，而不是把数量直接塞进识别关系表。

## 3. 推荐交互方案

导出对话框中：

- 每个鸟种显示一行；
- 提供可编辑数量；
- 默认值为 1；
- 用户可以逐行修改；
- 数量只在本次导出任务中有效；
- 导出结束后不保存到数据库；
- 不写入 Sidecar；
- 不修改 `records`；
- 下次导出重新使用默认值 1。

这样能满足 Excel 模板需求，同时保持现有数据模型稳定。

## 4. 数量校验

数量必须是正整数。

以下输入应校验失败：

- 0；
- 负数；
- 小数；
- 空字符串；
- 非数字文本；
- 超出合理整数范围的输入。

错误应在导出前明确提示，不应静默转换。

## 5. 导出失败与取消

- 用户取消导出，不修改数据库。
- Excel 文件创建失败，不修改数据库。
- 中途导出失败，不修改数据库。
- 用户修改的临时数量不应被保存为永久数据。
- 每个鸟种和汇总行的数量必须正确对应，不能串行或错位。

## 6. 边界用例与自动化断言

至少覆盖：

1. 所有鸟种默认数量为 1。
2. 用户修改某个鸟种数量后，导出结果使用修改值。
3. 修改一个鸟种数量不影响其他鸟种。
4. 0 被拒绝。
5. 负数被拒绝。
6. 小数被拒绝。
7. 非数字文本被拒绝。
8. 用户取消导出后数据库无变化。
9. 导出失败后数据库无变化。
10. 导出完成后 `records` 表没有新增或修改数量字段。
11. Sidecar 内容没有因为本次导出数量而改变。
12. 导出的每个鸟种数量与用户输入一致。

建议增加：

`verify_birdreport_export.py`

或者按照当前项目 `verify_*` 测试脚本风格命名。

## 7. 验收标准

- 导出对话框能够为每个鸟种设置数量。
- 默认数量为 1。
- 数量校验严格。
- 导出结果正确。
- 不修改 `records`。
- 不写入 Sidecar。
- 取消和失败不会产生持久化副作用。

# 三、总体实施顺序建议

六个专题不要机械地按照编号顺序开发。

建议优先级如下：

| 顺序 | 专题             | 建议                               |
| -- | -------------- | -------------------------------- |

# 四、1.0-test 连续开发的工程纪律

## 1. 数据库迁移

每次数据库结构变更必须：

- 修改前备份；
- 只加不删；
- 不破坏已有数据；
- 迁移前后记录关键表计数；
- 迁移失败能回滚或安全退出；
- 旧数据库能够升级；
- 重复运行迁移不会产生错误；
- 提供对应自动化验证。

不要为了实现新功能重构现有成熟数据模型。

## 2. Windows 便携版边界测试

需要形成一份便携版边界测试清单，至少覆盖：

- 中文用户名目录；
- 中文照片目录；
- 路径包含空格和特殊字符；
- 安装目录只读；
- 数据目录只读；
- 外置硬盘断开；
- 外置硬盘盘符变化；
- 长路径；
- 高 DPI 显示；
- 普通 DPI 显示；
- 杀毒软件锁定文件；
- 文件正在被其他程序占用；
- 程序异常退出后再次启动；
- 数据库文件异常或损坏；
- Sidecar 不存在、只读或内容异常。

## 3. 测试纪律

每项功能都要有功能级自动化验证。

优先沿用当前已有的：

- `verify_*`
- `assert_pkg`
- `frozen_check`
- 冒烟测试

不要只靠人工点击确认功能完成。

每个专题完成后先跑对应验证，再继续下一个专题。

最后统一执行：

- 数据库迁移测试；
- 旧版本数据兼容测试；
- Sidecar 兼容测试；
- 全部 `verify_*`；
- 打包检查；
- Windows 便携版检查；
- 核心功能冒烟测试。

## 4. 1.0 的验收方式

不要用“新增了多少功能”定义 1.0。

应该用验收清单定义 1.0：

- 原有核心功能没有退化；
- 旧数据库能够正常升级；
- Sidecar 兼容；
- 用户原图安全；
- 导入中断可恢复；
- 人工确认优先于 AI；
- 版权信息统一；
- 导出数量准确；
- 增量扫描不会误标 missing；
- Windows 便携版在常见边界环境下可靠；
- 第三方许可和发布声明清楚；
- 所有关键功能有自动化验证。

# 【评审补充】（开发智能体，2026-11-18）

以下四条为实施层补充/纠偏，与上文冲突时以本节为准：

1. **move 模式同卷快路径**：同卷移动先尝试 `os.replace()`/`os.rename()`（原子、瞬时、零双倍 I/O），成功即登记入库；跨卷或 rename 失败才走"copy→校验→原子改名→入库→删源"补偿流程。专题1 的补偿式设计默认适用于跨卷场景，不要对同卷移动也强制双倍 I/O。
2. **专题5 photo_copyright 可简化**：三态语义（继承/覆盖/明确清空）必须保留，但实现允许用单 JSON 列（`{"creator": {"v": "张三"} | null | 缺省}`：有值=覆盖、null=明确清空、缺省=继承）替代每字段两列的宽表，加列不加表、按工作树现有风格定。
3. **专题4 重开条件写死**：仅当真实用户反馈"查重漏报裁切/重导出版重复"案例 ≥3，或竞品实证该能力为刚需时才重开评估；否则 1.x 也不做。当前结论=两层（SHA-256 + pHash）+人工确认，③按此实现。
4. **专题1 staged 临时文件规范**：统一命名 `.birdtrace-imp-<jobid8>-<idx>.tmp`；启动恢复时清理本库目录下残存该前缀文件（核对 job 归属后才删）；启动恢复查询 status 非终态任务必须走索引，不扫全表。
